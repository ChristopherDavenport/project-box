## What the round found instead of what it measured

**The roles block never reached the agent.** box.yaml asked for effort
`high` on both roles; the planner's session record asserted `xhigh`, its
harness layer digest was the same digest round 5's session-less builders
carried, and the transcript showed all 53 requests at xhigh. The daemon built
the harness source from the box's model and session and never handed it the
roles, so the tier resolver found no role and fell back — and nothing on the
chain could say so, because a session option nobody requests is never
asserted. Fixed in #42 with a daemon-level test that fails on exactly that
shape. Chris chose to let the round finish as the xhigh control; the daemon
was restarted on the fix between the second and third units, and the third
asserted `high` at the wire, with every request in its transcript at high.
Its numbers are not an effort measurement: it was the smallest unit by
design, the data-model half of an approval binding.

**The meter charged a wait as a run.** The pump acquires the meter's start
before the loop tries the section leases. The whole-repository unit was
claimed while the view unit held the room section, went to waiting, and was
refused when the section freed: `max_per_window: 4`, with three agents
actually run. The window is clock-aligned, so the round would have sat idle
until the hour turned. The cap is 5 now, with the reason beside the number,
until the meter counts a start when an agent starts.

**A restart keeps the count.** The meter restores its window from the chain,
so a daemon restarted mid-hour still refused; a reload with the raised cap is
what let the unit claim. That is the right behaviour and worth knowing.

**The room showed almost none of it.** Tool calls became frames on an
in-memory ring the Sessions page rendered only while a unit was claimed, and
only from the moment the page opened; the item page showed the chain and
never a frame; the planner had no hook at all; and a Read or a Bash arrived
untitled. When a run ended, the ring was all there was. #44 gave the planner
the hook, made the item's stream replay the run so far, put an Agent card
on the item page, live and from a run log afterwards — telemetry in the
store beside the chain, pruned by age under `runs.keep_for` — and blamed
the untitled rows on the adapter titling a call on the update that follows.
That part was wrong. Round 7's first run on the #44 binary still showed one
title in 32 calls, and the adapter's raw wire showed titles on every call.
The runtime's wire struct typed an update's `content` as the message
chunk's object; on a tool call it is a list; the decoder's type error made
the handler drop the whole event, and a notification's error goes nowhere.
Every titled update the adapter sent with content — most of them — and
every completion vanished, with nothing on the record. Fixed in #48,
which also counts an update that fails to parse, so the next drift shows.

**A whole-repository unit has no check to run while it iterates.** The
builder is told its section's check; an unsectioned unit has none, and this
one reached for `go build ./...`, which fails in a workspace without the
generated web bundle. It reasoned its way past ("pre-existing environment
issue") and the gate, which generates the bundle, passed it — but a builder
should not have to guess. The repository's own check is the right default
for a unit that names no section.
